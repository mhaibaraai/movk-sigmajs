## 用法

本站示例的数据全部取自 sigma 官方 v4 网站的 `wikipedia.json`：维基百科上数据可视化相关词条构成的引用网络，2085 个节点、5409 条边、24 个社区，坐标由上游预先跑好。

完整数据集放在 `docs/public/data/wikipedia.json`，点击加载即可看到它渲染出来的样子：

:component-example{name="WikipediaDatasetExample" client-only="true" class="example-stage"}

## 原始数据不是 SerializedGraph

拿到的文件几乎不会正好是 graphology 的序列化格式，这份也一样：

```ts
interface WikipediaDataset {
  nodes: { key: string, label: string, tag: string, URL: string, cluster: string, x: number, y: number, score: number }[]
  edges: [source: string, target: string][]
  clusters: { key: string, color: string, clusterLabel: string }[]
  tags: { key: string, image: string }[]
}
```

节点是扁平行而不是 `{ key, attributes }`，边是元组而不是 `{ source, target }`。直接把它塞给 `SigmaGraph` 的 `data` 会立刻抛错：

```text
[@movk/sigma] data.edges[0] 缺少 source 或 target，需要 graphology 的 SerializedGraph
（graph.export() 的产物）。收到的字段：0, 1
```

::note
这是刻意抛错而不是静默跳过。形状不匹配时 `attributes` 恒为 `undefined`、每条边的端点都查不到，图会「加载成功」却空空如也——那种失败远比一条点名字段的异常难查。
::

## 装载归使用方，sigma 只渲染

上游的立场是 graphology 拥有数据、sigma 只负责渲染，装载这一步不在库的职责内。所以转换写在自己的函数里，把原始行喂给 `graph.addNode()`：

```ts [app/utils/wikipedia.ts]
export function toWikipediaGraph(dataset: WikipediaDataset) {
  const graph = new Graph()

  for (const node of dataset.nodes) {
    graph.addNode(node.key, {
      label: node.label,
      x: node.x,
      y: node.y,
      cluster: node.cluster,
      score: node.score
    })
  }

  // 原数据集里同一对端点会重复出现，非多重图上必须去重
  for (const [source, target] of dataset.edges) {
    if (graph.hasNode(source) && graph.hasNode(target) && !graph.hasEdge(source, target)) {
      graph.addEdge(source, target)
    }
  }

  return graph
}
```

建好的实例走 `graph` prop 传进去，`SigmaGraph` 完全不碰数据，只负责渲染与生命周期。用 `data` 走增量 diff 的场景则要自己 `graph.export()` 一次。

## 视觉映射交给 styles

注意上面**没有**写 `color` 与 `size`——这份数据本来就不带这两个字段，而 v4 的正确做法不是在建图时算好塞进属性，是让 `styles` 在渲染期从语义属性映射出来：

```ts
const styles = {
  nodes: {
    label: { attribute: 'label' },
    color: { attribute: 'cluster', dict: clusterColors, defaultValue: '#94a3b8' },
    size: { attribute: 'score', min: 3, max: 18, minValue, maxValue }
  }
}
```

`dict` 是分类映射（社区 key 到颜色），`min` / `max` 加 `minValue` / `maxValue` 是数值映射（score 区间线性缩到尺寸区间）。这么写的好处是改视觉不用重建数据，也不用为了配色遍历一遍两千个节点。

::warning
`styles.nodes` 会**整体顶掉** sigma 的 `DEFAULT_STYLES.nodes`。`SigmaGraph` 默认帮你合成回去，不然标签、`isHidden` 可见性与悬浮反馈会一起消失。细节见 [`composeStyles`](/docs/utils/compose-styles)。
::

三个字段的坑各不相同：

::field-group
  :::field{name="color"}
  节点自身不带颜色，得按 `cluster` 去 `clusters` 里查出一张字典。查不到时给 `defaultValue` 兜底，不要让 `undefined` 流进渲染。
  :::

  :::field{name="size"}
  节点自身不带尺寸，`score` 是唯一的重要度信号，上限 0.042。用数值绑定把它映到 3~18，不必自己算 `10 + score * 1000`。
  :::

  :::field{name="分类字段"}
  看起来该用 `tag`，实际上 2085 个节点里有 1194 个是 `"unknown"`，做不了分类。分类一律用 `cluster`。
  :::
::

::note
这类「字段名对得上、语义对不上」的坑只能靠先量一遍数据发现。接一份新数据集之前，先把每个字段的取值分布打出来看看。
::

## 坐标跨度决定要不要切 screen

原始坐标的跨度是 2860 个单位。sigma v4 的 `size` 默认是图坐标单位，3~18 落在这个跨度上会小得看不见。两条路：把坐标归一化到与 `size` 匹配的量级，或者让 `size` 不再依赖坐标：

```vue
<SigmaGraph :graph="graph" :styles="styles" :settings="{ itemSizesReference: 'screen' }" />
```

坐标由上游预先跑好、量级不受自己控制时，后者更省事。详见[节点尺寸与坐标量级](/docs/guides/node-size)。

## 大文件不要在挂载时加载

886 KB 的数据集加上 2085 个节点的建图，放进 `onMounted` 会让整页卡住，而且用户未必会看这个示例。示例里用一个按钮把加载推迟到真正需要的时候；入门页那个则走 `useAsyncData(..., { server: false })`，既不阻塞 SSR 也不把原始 JSON 塞进 payload。

万级节点的完整策略在[大规模图](/docs/guides/scale)里。

## 小示例用的是它的子集

本站其余示例调的 `demoGraph()` 不去 fetch 这个文件——它是同步函数，示例里 `const data = demoGraph()` 一行就要拿到数据。它读的是一份 160 节点的子集，随包打进 bundle，从 `docs/app/data/wikipedia-subset.json` 同步 `import`。

子集由脚本从完整数据集派生，从度数最高的节点做 BFS 展开，重新生成：

```bash
node docs/scripts/build-wikipedia-subset.mjs
```

`demoGraph({ nodes })` 再从子集里取一块连通子图，节点 key 重编为 `n0..nN`，`n0` 恒为整张图的枢纽。示例与文档正文都按这套稳定 id 引用节点，换数据源不会失效。它同样只产语义属性（`label` / `category` / `degree`），配套的视觉映射是 `corpus.ts` 导出的 `demoNodeStyle`。

::note
规模示例用的 `createScaleGraph()` 仍然是合成数据。那些示例要 2k / 5k / 20k 个节点，官方公开数据目录里最大的图也只有 2085 个——上游那批万级数据集是构建时从 SNAP 下载、不入库的。规模示例讲的是体量不是语义，合成数据反而能精确控制节点数。
::
